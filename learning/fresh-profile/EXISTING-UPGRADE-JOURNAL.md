# Existing Account upgrade journal

This entry is separate from the fresh bootstrap DAG. It does not create a cluster or run database bootstrap or migration. The staged adapter is enabled only by the normal runner factory after both the fresh sealed gate and the independent, time-bounded upgrade approval validate. A direct adapter instance remains mutation-disabled. No actual upgrade approval or reviewed replacement revision is provided by the repository.

The entry requires `--mode existing-upgrade`, an absolute `--live-plan`, independent `--approval` and `--journal`, plus `--gate-approval`, `--gate-plan`, `--materialization`, `--profile`, `--platform-source-root`, and `--application-source-root`. The upgrade approval binds the exact plan bytes. The plan binds the fresh target and UIDs, protected resource UID/resourceVersions, the old and new application revisions, controller bundle and rollback inputs, the existing admission policy identity and stage hashes, the Git/Helm/kustomize executable hashes, and the reviewed Git desired chains. The sealed gate independently validates its approval, source set and image-supply lock. Neither the plan nor journal should contain Secret values.

The forward actions are `policy-initial`, `pause`, `prepare-continue`, `continue`, `policy-new-paused`, `account-continue`, `policy-final-automated`, and `restore-continue`, in that order. The last action records `outcome: upgraded` only after the new desired chain, rollout runtime and full Application sync are observed. To roll back a completed upgrade, or a new sync whose bounded operation has terminated but failed or has not converged, first use read-only `resume`, then `policy-rollback-paused`, `rollback-continue`, `policy-rollback-old`, and `rollback-restore`. The failed operation must have a matching nonce, revision and exact non-pruning scope, and it must no longer be active. An unknown receipt or active operation stops the workflow without resending it. The last action records `outcome: rolled-back` only after the original desired chain and old controller are observed. The older `first` and `rerun` synthetic executor path is not the staged live mutation entry.

Each write has a durable journal intent and is scoped to a known object or explicit resource allowlist. Existing objects use UID/resourceVersion and old-value tests; initially absent Role and RoleBinding use create-only operations, with returned UIDs recorded. Their rollback uses `DeleteOptions` UID and resourceVersion preconditions through fixed Kubernetes API paths. Account sync specifies the five workload-only resources and `prune=false`. A failed or unverified write is uncertain. `resume` only observes and never resends; once it proves an outcome, a separate action may continue. A lost create response before its UID is recorded remains uncertain. A renewed approval for the same plan is accepted through observation-only `resume`.

The verifier renders the original pre-pause root, parent and child from their immutable Git revisions, including the old two-parameter automated chart. It also renders the initial paused, new paused, final automated and old rollback chains. The staged existing admission-policy specifications must match the fixed policy template with only the reviewed pins substituted. The old and new workload renders must have identical complete protected objects and no changes outside the Account sync allowlist; external Secrets must be absent from both renders. Completed Jobs and the bootstrap ConfigMap are not recreated, and live protected UIDs/resourceVersions are checked throughout. Auto-sync restoration requires an exact fully Synced Application revision, the rendered desired chain, protected identities, database ACLs, and running Pod/rollout observations. The rollout must have all desired replicas updated and ready; a paused or incomplete rollout does not pass this check.

The adapter outputs only Secret metadata through JSONPath. The Kubernetes API still returns the Secret object to kubectl, including its data; those values are not printed or journaled. The database prerequisite executes a read-only catalog query inside the existing PostgreSQL Pod. It checks accounts CRUD, migration-history SELECT without INSERT/UPDATE/DELETE, and absence of effective sequence and matching default grants. It returns only `ok` or `not-ok`; it does not repair privileges or print credentials or application rows.

A Cloud comparison of application commits `3707f73581da5d04db0e4771dda7c1e82bd0f47c` and `77e8c465cd96fe84926dd337cd96fccf029b9d99`, using Git archives and `kubectl kustomize`, found different rendered `ConfigMap/account-role-bootstrap` and `Job/account-migration` objects. The other four rendered protected objects compared equal, so the equality contract rejects that transition. The working-tree `learning/fresh-profile/workload-existing` variant preserves the old two Jobs and bootstrap ConfigMap while updating canary resources. It needs a separately reviewed and approved immutable revision; the repository does not assert that one exists.

This workflow assumes one operator during a maintenance window. UID/resourceVersion tests, operation checks and before/after observations detect many conflicts, but another actor can still change resources between checks. The normal CLI has been exercised with synthetic Git commits, approvals and a fake transport; this is not evidence of a live-cluster run.

The old `3707f735` workload has four selectable Account resources and no `AnalysisTemplate/account-api-policy`. Rollback sync therefore targets only those four resources and does not prune. The new overlay's AnalysisTemplate is expected to be absent before the upgrade; after the forward sync its UID and Argo tracking annotation are recorded and checked. Rollback retains that unused template, with `IgnoreExtraneous` and `Prune=false,Delete=false` annotations, rather than deleting it. Argo's IgnoreExtraneous option affects sync status only: it does not guarantee application health. Rollback still requires an observed full `Synced` status at the old revision; absent, changed or untracked retained-template evidence stops the workflow. Any later cleanup is a separate operation and is not performed here.
