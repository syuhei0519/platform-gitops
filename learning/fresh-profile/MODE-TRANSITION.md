# Reviewed promotion mode transition

`runner.py --mode mode-transition` requires a separately approved plan, the sealed live gate and its approval, both source roots, and an absolute journal path. `--mode-action first` starts a new journal; `resume` only observes an uncertain operation; `continue` advances after observation has established the preceding outcome. A renewed approval for the same exact plan can be recorded only during `resume`; a separate `continue` is required for later writes. The plan pins the old and new paused platform, chart and workload Git commits, an optional initial automated Git desired state, mode and workload variant, image, tool hashes, Application and Rollout identities, policy identity, and protected resource identities. A final automated desired state is optional and must be separately pinned in the same approved plan. Existing pins and approvals are not created by the runner.

The renderer reads Git commit archives and runs the pinned Helm and kubectl executables. It checks the exact parent and child desired state, the corresponding staged existing admission policy, and that the workload render changes only the three promotion pauses. When initial automated desired is supplied, the journal first changes the existing policy and root, parent and child desired to the reviewed paused state. The journal applies each policy and Application spec with UID, resourceVersion and spec tests. It then requests a Rollout-only Argo sync with prune disabled and requires a matching successful receipt and stable Rollout with the reviewed mode steps. An unknown or failed sync is never resent; it remains in the journal for observation and requires a separately reviewed recovery if it cannot be proved successful.

When a reviewed final automated state is supplied, an explicit `continue` restores its policy and Git desired only after the selective sync receipt, full Argo Synced status, stable Rollout and protected UID/resourceVersions are observed. If final is absent the child stays paused. The protected identity check uses kubectl JSONPath output; Kubernetes still returns the Secret object to kubectl even though values are neither printed nor journaled. This is intended for a single operator in a maintenance window. UID/resourceVersion checks and observations detect conflicts, but do not provide a cross-object transaction or exclude other actors between observations.
